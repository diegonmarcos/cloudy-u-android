# #1869 Why opening mail felt slow, and what changed

Scope: the open paths of Cloud Mail (app start, folder list, message reader) and the background
sync that should keep the last 90 days local. Method: the open paths were read call by call from
the tap to the first frame, and every wait was classified as local (Room, the core store, CPU) or
network. The device timings come from the log tags already in the app: `MailOpen` (phases of
`openMessage`: `open-from-cache`, `fetch-email-get`, `inline-images`, `open-from-network`,
`webview-warmup`), `MailPrefetch` (list and neighbour prefetch) and `OfflineSyncWorker` /
`MailCoreSyncWorker` (one line per background pass). CI cannot run a device, so the on-phone
check of the numbers below is still pending.

## What was already local-first (kept as it is)

| Path | Source | Network on open? |
|---|---|---|
| Folder list | Paging over Room (`pagedFolder`, `pagedMailbox`), mediator `SKIP_INITIAL_REFRESH`, stable keys `accountId\|id` | no |
| Reconcile on a change of view | `refreshUnlessFresh`, background, 30 s freshness register | runs behind the rows |
| Message body | `openMessage`: decrypt cache (memory), then the Room body cache, then the network | only on a cache miss |
| Background window | `OfflineSyncWorker` -> `FullSync` (JMAP: Email/changes, header backfill to the window edge, bodies of every folder, attachments by policy), `MailCoreSyncWorker` (core store) | background |
| Window | "Keep mail offline for", `OfflineWindow.DEFAULT = THREE` (90 days); per account `SyncWindow.DAYS_90` | - |
| Indexes | `emails(accountId, mailboxId, sortKey)`, `email_mailboxes(accountId, mailboxId)`, `email_bodies` PK `(accountId, id)` | - |

The window was not too small (90 days is the default on both settings) and the list query is
indexed and paged. The lag came from the places below.

## Root causes found

1. **The reader waited on the network even with the body on disk.** `MessageViewModel.load` started
   the core's raw-message fetch (`coreReaderFetched`) whenever the core store lacked the message,
   then, after `openMessage` had returned the cached body, waited for that fetch with
   `withTimeoutOrNull(CORE_FETCH_WAIT_MS = 2000)` before drawing the body. Any message the core
   prefetch had not reached (every folder but the newest Inbox pages) therefore opened up to 2 s
   late, over a network round trip, with its body already in Room. Offline the wait ran to the full
   2 s. This is the main open-path lag.
2. **Neighbour prefetch stopped at the Inbox.** `prefetchNeighbours` returned for every folder that
   was not the Inbox, so a swipe to the next message in Archive, Sent, a label or any user folder
   was a cache miss and a network fetch whenever the background window had not reached it yet.
3. **Cached bodies were decoded on the main thread.** `cachedMessage` (called from the reader's
   `warmFromCache` and `load`, both on `viewModelScope`, i.e. `Dispatchers.Main.immediate`) decoded
   the stored body JSON on the caller's thread. A large HTML newsletter is hundreds of KB of JSON:
   a visible frame drop on every open from cache.
4. **Inline images were never prefetched.** The full sync stored bodies with an empty inline-image
   map, so every message with `cid:` images fetched them over the network after opening (text
   first, images popping in later), and offline they never appeared.
5. **A spinner over cached rows.** The pull-to-refresh tern was drawn for every background
   reconcile that outlived its 250 ms grace (folder tap, cold start), over a list that was already
   complete from Room. The list looked like it was loading when it was not.
6. **App-start sync was not expedited.** `OfflineSyncWorker.runNow` and `MailCoreSyncWorker.runNow`
   were plain one-time requests (and the offline sync also required battery-not-low), so the
   window could start warming minutes after the app was opened.

Not causes, checked and ruled out: the list query (indexed, paged, keyed); the sync window size
(90 days by default on both settings); decryption (an encrypted message is decrypted only on
demand and the plaintext stays in a memory LRU, by ENCRYPTION.md; it was never on the plain-mail
open path); the WebView start-up (already warmed off the open path by `WebViewWarmUp`).

## What changed (#1869)

| Cause | Fix |
|---|---|
| 1 | The open path never awaits the core fetch: a document already fetched is used (`completedOrNull`), one still in flight lands in the core store for the next open. `CORE_FETCH_WAIT_MS` is gone. |
| 2 | Neighbours are prefetched in every folder. The Inbox keeps its pinned path; every other folder goes through the raw store (`fetchAndStoreRawBodies`), which never imports a key (the #1768 rule). |
| 3 | `cachedMessage` reads and decodes on `Dispatchers.Default`. |
| 4 | `FullSync` gained an inline-image phase after the bodies: unmetered and not on battery saver, inside the body cap, `FULL_SYNC_INLINE_PER_RUN` messages per run, continuation when the budget is spent. Encrypted bodies are skipped. |
| 5 | With cached rows on screen the tern answers the pull gesture only; a background reconcile draws a one-hair progress line at the top of the list instead (`RefreshDisplay.kt`). An empty list keeps the tern. |
| 6 | Both `runNow` requests are expedited on Android 12+ (out of quota: normal work), with network-only constraints; the engine still stops on battery saver at every step. |

Encryption semantics are unchanged: ciphertext is stored as received outside the Inbox and never
cached inside it, nothing decrypted is persisted, and no background path imports a key outside the
Inbox.

## Second pass: the open path as one local read (design review steps 1-4)

A design review of the open path (fable-open-path-design.md, 4___ASSETS___/1869) ranked main-thread work and a serial
chain of local hops above the cache gaps. Steps 1-4 of its plan are in:

| Step | Change |
|---|---|
| 1 | `AccountStore` memoises decrypted secrets, keyed by account id AND the stored ciphertext, so a write can never be answered stale. The reader's local reads (`warmFromCache`, the snapshot) take the account id only; credentials are resolved after the paint. |
| 2 | `LocalReaderStore.snapshot(accountId, emailId)`: the body (stored, or this process's decrypted copy), the list row, the stored core document and the snooze in ONE IO hop, `Hit` or `Miss`. `load` paints from it; the header-only repaint is skipped on a `Hit`, so the page is painted once. |
| 3 | No network in `load` before the paint: `coreReaderFetched` left the open path (`queueCoreFetch` fills the core store in the background; the core document is used only if already stored and is never swapped in after paint). The `NoNetwork` coroutine-context tripwire makes `connect()`, `coreReaderFetched` and every IMAP session throw under the snapshot. |
| 4 | The reader document is built on `Dispatchers.Default` (`produceState`, keyed to the message id), the sanitiser runs once per body (a memo in `ReaderBody.kt` in front of the one policy function), and the unsubscribe body scan runs on `Dispatchers.Default`. |

Steps 5-11 of the review (schema v34 with stored fragments and an `email_parts` table, inline images as files served
through `cid:` interception, neighbours in pager order and a VISIBLE trigger, planner fixes for metered text, calendar
parts, IMAP batches and local ciphertext, a WebView pool, the tap handoff, the conditional fade, an offline read-state
queue) are not done yet.

## Third pass: design steps 5-11 (phase 2)

| Step | Change |
|---|---|
| 5 | Room v34, additive and registered (`MIGRATION_33_34`): `email_bodies` gains `fragment`, `fragmentVersion`, `inlineState` (0 = unknown, classified lazily) and `bytes` (backfilled once from the old `LENGTH` sum); new table `email_parts` (attachment metadata, the cid-to-file index). The body caps and the eviction plan read `SUM(bytes)`, so no cap query reads body text. |

## Kept as is, noted for later

- IMAP accounts still fill their window through `syncOffline` (one fetch per message) and get no
  list or neighbour prefetch; JMAP is the fleet's protocol and the target of this ticket.
- On a metered link the full sync takes the incremental headers and the newest 25 bodies per run
  and leaves the backfill to Wi-Fi (the #1763 throttle).
- Both workers run on app open (Room path and core store); they share the server but not the work.
